# API payload and round-trip audit — 2026-10-29

This is a source audit of the current working tree, not captured production traffic
or a latency/cost benchmark. It covers every route registered in `src/http.rs`, the
model/identity/embedding/push adapters, and the existing sibling Flutter account and
readiness consumers. The sibling client was read only. Native chat, memory,
project, realtime and push consumers are not implemented there; their future traffic
is not counted as existing behavior. Runtime verification limitations are in
[status](../status.md).

## Result and priorities

The backend already avoids the largest avoidable round trip: clients submit the
new turn and owned attachment IDs rather than the entire transcript. Context is
assembled internally; a normal text reply uses one hosted generation request.
Retries and reconnects reuse the accepted request. Background extraction and
summary generation share one additional bounded request per eligible eight-turn
batch, rather than separate calls on each message. There is no hosted embedding,
memory or vector-search service.

| Finding | Impact | Disposition |
| --- | --- | --- |
| Small JSON routes previously inherited the 8 MiB attachment body cap | Parsing/allocation could exceed the useful content bound before rejection | Fixed: default metadata/memory/project/device cap 16 KiB, turns 256 KiB, auth/profile JSON 8 KiB, attachments 8 MiB and avatars 2 MiB. Escaped valid text fits; field limits still apply. |
| Flutter linking exchange returns the full account, then `AuthController.provider` fetches `/account` again | One redundant request and profile payload per successful link/refresh | Outstanding coordinated client fix: `../smartcindy-app/lib/account/auth_controller.dart:329`. Apply the same account-ID and linked-method checks to the returned account, retaining the proof exchange. The backend already verifies the initiating session within exchange. Sibling files were not changed here. |
| Flutter removes a custom photo with DELETE, then fetches `/account` | One extra request for an already-known `has_custom_avatar=false` transition | Client follow-up: update that cached property after successful 204, retaining known provider fallback metadata. Current contract is correct; no backend-only response change was made. |
| Signup/login/provider sign-in return a session, then Flutter requests the profile | Two serial requests before the profile is ready | Necessary under the current contract. A coordinated optional profile in the successful session response can remove one trip; requires schema, client and authentication tests together. Do not weaken account-ID checks or session validation. |
| Custom avatar is fetched again on explicit profile refresh | Repeated image bytes if unchanged | Retain privacy and identity invalidation. Consider a small account-scoped in-memory cache keyed by a returned avatar version; the current API has no avatar version/conditional validation. Do not cache solely by user ID indefinitely. |
| Historical photos within the selected recent text context are re-encoded and sent again | Up to 32 MiB of image bytes, about 43 MiB after base64, per request before JSON overhead | Bounded but potentially dominant. Retain correct visual follow-ups now; measure and design explicit image-reference selection before dropping images on topic switches. Provider cache discounts do not remove upload bytes. Image-output requests use only current input photos. |
| Image-output preparation built an unused DeepSeek-style image payload | Extra local allocations/base64 copies; no extra external request | Fixed in `provider::context`: image output now retains one base64 input per current photo and does not build unused data URLs or append unused message objects. This is a source-level reduction, not a measured speedup. |
| Message and branch pages were bounded by count alone | Large pages could approach 6.4 MiB before metadata/escaping | Fixed: 512 KiB serialized-response target, whole records and continuous cursors; no text truncation. The first record is always returned to guarantee progress. Count limits remain; future clients should still request the visible window. |
| Empty chat creation lacked retry identity | Retrying after a lost response could create duplicate chats | Fixed: optional `request_id` returns the same chat on matching replay, 409 on changed creation input and 410 after deletion. Clients must supply it for safe retries; omission remains supported. |
| Repeating an unchanged device registration advanced its version and cancelled pending notifications | Routine client retries could suppress a completion alert | Fixed in source: identical same-session registrations preserve the record, timestamp and queued delivery. Registration changes still invalidate stale deliveries; runtime regression execution is blocked by Docker access. |
| Generation SSE polled auth/status and events separately each 200 ms | Two database round trips for each poll | Fixed: one SQL snapshot checks auth/ownership/deletion/status and reads up to 32 events. Theoretical idle ceiling is now ~5 reads/sec/subscriber, or ~160/sec if all 32 shared stream slots are generation streams, not a measured rate. Realtime invalidation streams poll once/sec. A later measured notification-wakeup design must preserve revocation and replay. |
| BFL polls at 500 ms while pending/processing | Additional provider HTTP requests while awaiting one paid image generation | Retained to preserve current response timing. Measure completion distributions before adopting capped adaptive polling; never retry image submission to reduce polling. |
| JSON error code/message duplicate the same sanitized value; `attempt_id` and some profile metadata are currently unused by Flutter | Small extra payload | Deliberate stable contracts; changing them offers little benefit compared with images and redundant requests. Keep security, version, identity and provenance fields. |

## Public route inventory

All paths below include `/v1` except `/healthz`. Owned endpoints use the bearer
header, not repeated user IDs in bodies. Responses are `Cache-Control: no-store`.
`?` denotes optional input. Common failures return the sanitized error envelope;
successful DELETEs generally have no body. Body limits, authentication and source
checks are retained even where omitting them could save work.
Metadata bodies are capped at 16 KiB, turns 256 KiB, auth/profile JSON 8 KiB;
the separate binary image caps appear below.

Reusable response shapes:

- **Session:** `token, expires_at, user_id`.
- **Account:** `id, email, display_name, display_name_source, avatar_url,
  has_custom_avatar, methods, capabilities {email_change,password_change}`.
- **Chat:** `id, title, project_id, archived, version, head_id, created_at, updated_at`.
- **Message:** `id, parent_id, role, parts, depth, order, created_at, generation_id, status`.
- **Memory:** `id, content, version, source_chat_id, source_message_id, created_at, updated_at`.
- **Project:** `id, name, version, created_at, updated_at`.
- **Page:** `items, next_cursor`; message pages additionally return the pinned `head_id`.
- **Usage:** input/output/total tokens, with cached/uncached input counts only when
  supplied by the model. Missing counts are not inferred as zero or billed dollars.

The selected BFL adapter does not currently expose a monetary price or provider
usage settlement comparable to text tokens. Do not claim total API dollars saved
from these token counters alone. Search/Fetch, research loops, reminders and email
delivery are not outbound operations implemented in this audited slice.

Push delivery is separate from model generation. Its durable outbox allows at most
three delivery attempts within a one-hour lifetime, respects retry delay, checks
session/device/chat validity and clears settled payloads. A transport ambiguity can
still deliver twice; this is not an exactly-once claim. The same chat/generation IDs
and deep link support app routing, while platform categories/click actions support
native notification controls. The small serialized `actions` string is an explicit
cross-platform contract, not conversation-history duplication. Copy/open actions
must resolve owned content in the app rather than placing the full reply in push.
No database connection is held during provider HTTP calls.

## Verification limits

Static route/adapter/client review completed. This document does not certify
minimal possible payloads or maximum performance. Full database HTTP journeys are
blocked in this environment by Docker socket denial; real model downloads and
embedding latency/quality checks are separately blocked. No paid-provider traffic,
charges, packet traces, real FCM/APNs deliveries or native end-to-end runs were
generated for this audit. Fixed findings above describe source changes; they do not
claim successful Docker-backed or device acceptance runs.

Retain idempotency, ownership, native proofs, versions, source attribution and
deletion fences. Prefer eliminating a redundant complete request or large image
payload before shortening stable field names or removing safety metadata.
